// Case Study

final class BankManagementSystem

A console-based banking application built to practice core Java, JDBC, and relational schema design — supporting multiple accounts per user, authenticated sessions, and full transaction handling.

Java JDBC MySQL Maven Solo project
View on GitHub ← Back to Projects

01Problem Statement

Most beginner Java projects stop at CRUD on a single table. I wanted something that forced me to reason about state and consistency the way a real banking system has to: a user can hold several accounts, every balance change must be atomic, and nothing should be trusted from the UI layer without validation on the way to the database.

The goal was to build a console application where:

  • Users authenticate before touching any account
  • A user can open and operate multiple accounts
  • Transfers between accounts either fully succeed or fully roll back
  • Every transaction is recorded and auditable

02Architecture

A layered console architecture: a thin CLI layer for I/O, a service layer for business rules (validation, transfer logic), and a DAO layer that's the only part allowed to talk to JDBC directly.

// request flow
Console (Menu/Input) → Service Layer (validation, business rules) → DAO Layer (JDBC) → MySQL

// key decisions
• Connection pooling via a single reusable DataSource, not a new connection per query
• Fund transfers wrapped in a single JDBC transaction (commit / rollback), never two separate updates
• Passwords hashed before storage, never compared or stored in plain text

04Database Schema

Four tables: users, accounts, transactions, and sessions. Each user can own several accounts; every transaction references the account(s) it touched.

TableColumnTypeNotes

05Internal API / Service Design

Not a REST API — this is a console app — but the service layer exposes a clean internal contract, structured the same way a REST layer would be if this were ported to Spring Boot.

MethodOperationDescription
POST/auth/loginAuthenticate user, start session
POST/accountsOpen a new account for the logged-in user
GET/accounts/{id}/balanceFetch current balance
POST/accounts/{id}/depositDeposit funds
POST/accounts/{id}/withdrawWithdraw funds, checked against balance
POST/transferMove funds between two accounts atomically
GET/accounts/{id}/transactionsList transaction history

07Challenges Faced

Race conditions on transfers

Two near-simultaneous withdrawals could both read the same balance before either committed. Fixed by wrapping the debit + credit in one transaction with row-level locking (SELECT ... FOR UPDATE) instead of separate read-then-write calls.

Connection leaks

Early versions opened a new Connection per DAO call and didn't always close it in the failure path. Moved to try-with-resources everywhere and a shared connection pool.

08What I Learned

  • Why transactions exist — this project is where "commit vs rollback" stopped being theoretical
  • The real cost of doing validation only in the UI layer instead of the service layer
  • How to design a schema around invariants (balance never negative) instead of trusting application code to enforce them
  • That connection pooling isn't optional past a handful of concurrent users

09Future Improvements

  • Port the service layer to a Spring Boot REST API with the endpoints above
  • Add JWT-based auth instead of an in-memory session
  • Add interest calculation and scheduled statement generation
